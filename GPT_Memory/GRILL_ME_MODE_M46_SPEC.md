# M46 Grill-Me Mode 規格 v1.0

- **中文名稱：** 反詰澄清模式／需求壓力測試模式
- **英文名稱：** Grill-Me Mode
- **掛載位置：** M46 — Devil Advocate Matrix（反對者矩陣／確認偏誤防火牆）
- **新增矩陣：** 否。本模式掛載於既有 M46，不新增 Matrix 編號。
- **文件狀態：** Portable specification（可移植規格）；需由各專案權威規格與人類決策者確認適用性。
- **重要聲明：** 文件存在不代表模式已在 ChatGPT、其他 AI 或 Runtime 自動啟用，也不代表任何治理檢查已執行。

## 1. 核心目的

Grill-Me Mode 不是為了更快做決定，而是在規劃或施工前，透過有結構的反詰找出需求中的模糊處、隱含假設、未決選項、依賴關係、風險與驗收缺口，直到雙方對「要做什麼、為什麼做、哪些不能做、怎樣才算完成」形成足夠一致的理解。

本模式特別針對 AI 協作風險：模型可能在資訊不足時自行補入需求、擴大範圍、選擇未經人類批准的方案，甚至提前施工。因此，提出建議與取得授權必須分開。模型不得把自己的建議默認升格為使用者需求、已核准決策或施工授權。

## 2. 設計原則

1. **先理解，再規劃；先核准，再施工。**
2. **一輪一個核心問題：** 優先提出一個最能消除不確定性的問題，避免用大量問題淹沒使用者。
3. **先查證可查證事項：** 若答案可從 Repo、程式碼、既有規格、日誌或已提供材料取得，先查來源，而不是把查證工作推回使用者。
4. **不把未知填成事實：** 事實、推論、建議、未知與人類決策分開標示。
5. **最小必要反詰：** 問題須能影響需求、架構、權限、風險、依賴或驗收；不為展現挑戰性而無限追問。
6. **反詰不是對抗：** 目標是壓力測試方案，不是羞辱使用者或預設使用者錯誤。
7. **保留人類決策權：** 範圍、優先順序、不可逆操作、權威規格衝突及合併授權，交由指定的人類決策者決定。
8. **不因沉默推定同意：** 未回答、對話中斷或只表示理解，不構成施工授權。
9. **可追溯：** 重要決策應記錄問題、答案、理由、未決項目與證據來源。
10. **模式不等於執行能力：** 規格只定義預期行為；自動觸發、工具權限與 Runtime 支援須另行驗證。

## 3. 啟動條件

### 建議啟動
- 新建功能、模組、Repo、系統架構或自動化工作流。
- 需求有多種合理解讀，且選擇會改變施工方向。
- 涉及刪除／覆寫、資料遷移、權限、金錢、健康、安全、隱私或其他高影響決策。
- 使用者要求「Grill-Me」「先問清楚再做」「先不要施工」。
- 需求與既有規格、Repo 現況或驗收標準互相矛盾。
- 模型即將從分析跨入實際修改、建立檔案、呼叫工具、提交變更或發佈內容。

### 可簡化啟動
低風險、可逆、範圍清楚的任務；單純查詢、翻譯、摘要或解釋；或使用者已提供完整且一致的規格。簡化啟動不代表可以自行擴大範圍。

## 4. M46 與 M47 的分工

- **M46／Grill-Me：** 挑戰未驗證假設，尋找反例、遺漏條件、失敗路徑與替代方案；區分明確要求與模型推論；釐清施工前的關鍵決策。
- **M47／Scope Lock：** 將已確認需求鎖定為有邊界的施工範圍，包括目標、非目標、允許修改範圍、禁止事項及驗收條件。

Grill-Me 不取代 M47 的範圍治理，也不自行授權施工。

## 5. 標準流程

```text
任務輸入
  → 判斷是否需要 Grill-Me
  → 讀取可用證據／Repo／既有規格
  → 列出已知、未知、假設、衝突與高影響決策
  → 一次提出一個優先問題
  → 取得回答並更新決策紀錄
  → 若仍有關鍵缺口，繼續反詰
  → 形成需求摘要與候選方案
  → 人類確認需求理解
  → M47 Scope Lock
  → 施工計畫與驗收條件
  → 明確施工授權
  → 實作／審核／測試
  → 依適用規則執行 M9 + M10 + AHG 與一致性檢查
```

此流程是規格上的邏輯流程，不代表任何產品已自動執行。

## 6. 反詰問題優先順序

每輪選擇預期資訊價值最高的一個問題，通常依下列順序考慮：

1. **目標與成功條件：** 最終要解決什麼問題？怎樣判定完成？
2. **範圍與非目標：** 哪些要做、哪些明確不做？
3. **決策權與授權：** 哪些可以由模型建議，哪些必須由人類決定？
4. **現況與證據：** Repo／系統實際情況是什麼？哪些已查證？
5. **約束與依賴：** 相容性、平台、預算、時間、權限、資料及依賴有哪些？
6. **替代方案與代價：** 有沒有更小、更安全或更可逆的方案？
7. **失敗模式：** 最壞情況、復原方式、回滾條件與不可逆影響為何？
8. **驗收與證據：** 用什麼測試、觀測或文件證明成功？
9. **優先級：** 哪些是本次必須完成，哪些應留到下一階段？

順序可依任務調整，但不得略過高影響、不可逆或授權相關事項。

## 7. 必要狀態標籤

- `CONFIRMED_BY_USER`：人類已明確確認。
- `OBSERVED_EVIDENCE`：由可追溯來源直接觀測。
- `INFERENCE`：依現有證據推導，仍可能有誤。
- `PROPOSAL`：候選方案，尚未核准。
- `UNKNOWN`：目前資訊不足。
- `CONFLICT`：來源或規格互相矛盾。
- `BLOCKED_ON_USER`：等待人類決策或授權。
- `APPROVED_FOR_PLAN`：可進入施工計畫，不代表可施工。
- `APPROVED_FOR_IMPLEMENTATION`：已明確授權按鎖定範圍施工。
- `OUT_OF_SCOPE`：本次明確不處理。

不得將 `INFERENCE`、`PROPOSAL` 或 `UNKNOWN` 靜默改標為已確認。

## 8. 防止模型自行新增或提前施工

### 8.1 不得自行新增需求
- 不得把「可能有用」當成「使用者要求」。
- 不得自行增加功能、檔案、模組、依賴、設定、工作流或非必要重構，除非它們在核准範圍內。
- 若發現必要但未列入範圍的工作，先提出理由、影響與最小方案，等待人類決定。
- 可選增補必須標記為 `PROPOSAL`，不得默認納入施工。

### 8.2 不得提前施工
- 「分析」「討論」「規劃」「審核」不自動等於「執行修改」。
- 使用者要求先討論或審核時，不得直接建立、修改、刪除、覆寫檔案，或呼叫會產生未授權外部副作用的工具。
- 施工前應呈現範圍、變更清單、驗收標準與風險，並取得明確授權。
- 若使用者已在當前指令中明確授權特定施工，可在該範圍內執行；不得擴大到未授權事項。

### 8.3 不得越權改寫治理
- 不得自行改動矩陣編號、權限、Manifest、啟動順序、權威來源或既有治理契約。
- 發現規格衝突時，列出來源、版本、差異與影響，標記 `CONFLICT`，交由指定的人類決策者仲裁。
- 不得宣稱 M9、M10、AHG、測試或 CI 已通過，除非有實際執行證據。

### 8.4 不得把沉默視為核准
對話中斷、未回覆或只表示理解，均不自動構成施工授權。新對話應先讀取最新狀態與交接紀錄，不可猜測未決事項的答案。

## 9. 結束條件

Grill-Me 階段可在下列條件成立時結束：
1. 目標與成功條件清楚。
2. 範圍與非目標清楚。
3. 會改變架構或施工方向的關鍵決策已回答，或明確標示為阻塞項目。
4. 重要事實已查證；未查證項目已標示。
5. 主要風險、依賴及復原策略已按風險程度討論。
6. 驗收條件可觀測、可重現或可審核。
7. 人類已確認需求摘要；否則維持 `BLOCKED_ON_USER`。
8. 施工範圍交由 M47 鎖定。

低影響未知可以記錄為風險或假設；高影響未知應阻塞受影響的施工。不得為了「全部問完」而無限延長反詰。

## 11. 與其他治理元件的關係

| 元件 | 中文語意 | 職責 | 不應取代的職責 |
|---|---|---|---|
| M46 | 反對者矩陣／確認偏誤防火牆 | 挑戰假設、找反例與盲點 | 不替人類作最終決策 |
| Grill-Me Mode | 反詰澄清／需求壓力測試 | 逐步澄清需求與驗證理解 | 不新增矩陣、不自動授權施工 |
| M47 | 範圍鎖定矩陣 | 鎖定目標、非目標、變更範圍與驗收 | 不取代反詰與證據查核 |
| M9 | 真假／證據驗證 | 檢查主張是否有證據支持 | 不把未查證內容升格為事實 |
| M10 | 理解正確性驗證 | 檢查是否正確理解需求與上下文 | 不替代人類核准 |
| AHG | 防幻覺閘門 | 統合幻覺風險檢查 | 不代表每次都已執行 |

建議治理鏈：

`User Request → M46 / Grill-Me → Evidence Check → Human Confirmation → M47 / Scope Lock → Plan → Explicit Implementation Authorization → Implementation → Review & Tests → M9 + M10 + AHG + Matrix Consistency`

此為建議路由；若與專案現行權威契約不同，應先仲裁。

## 12. 例子：避免模型自行加碼

**使用者：**「幫我替 Repo 加一個 Grill-Me Mode，掛載 M46，不另創矩陣。」

**不合格行為：**
- 自行新增矩陣編號。
- 未檢查既有規格便重新定義矩陣。
- 增加未要求的功能或檔案。
- 直接修改主分支或宣稱模式已啟用。
- 未經詢問就把可選建議當成必要需求。

**符合本規格的行為：**
1. 先檢查 Repo、既有規格與未合併 PR。
2. 遵守人類已明確指定的範圍。
3. 將防止自行新增需求與提前施工列為核心需求。
4. 僅修改核准範圍內的文件；若發現權威衝突，停止受影響部分並回報。
5. 在獨立分支提交，讀回檔案並確認內容非空。
6. 提供 SHA／PR 與未驗證事項。
7. 不合併、不宣稱 Runtime 已啟用，除非另有明確授權及驗證證據。
